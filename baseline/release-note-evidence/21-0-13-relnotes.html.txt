<h4><a id="R21_0_13" name="R21_0_13"></a>Java&trade; SE Development Kit 21, Update 21.0.13 (JDK 21.0.13)</h4>
<p>Release date: October 20, 2026</p>
<p>
The full version string for this update release is 21.0.13+10 (where "+" means "build").
The version number is 21.0.13. This JDK conforms to version 21 of the Java SE Specification (<a href="https://jcp.org/en/jsr/detail?id&#x3D;396">JSR 396</a> 2023-09-19).
</p>

<h4>IANA TZ Data 2026c</h4>

</p>
<ul class="obullets">
<li>Alberta moved to permanent -06 on 2026-06-18.</li>
<li>Morocco moves to permanent +00 on 2026-09-20.</li>

For more information, refer to
<a href="https://www.oracle.com/java/technologies/tzdata-versions.html">Timezone Data Versions in the JRE Software</a>.

<a name="NewFeatures"></a><h4>New Features</h4>
<p>
<div class="release-note"><a name="JDK-8347938"></a>
<div>security-libs/java.security</div>
<b><a href="#JDK-8347938"><span class="arrow">&#x279c;</span></a>&nbsp;Added Support for the Latest ML-KEM and ML-DSA Private Key Encodings
</b> (<a HREF="https://bugs.java.com/bugdatabase/view_bug?bug_id=JDK-8347938">JDK-8347938</a>)
<p></p>
<p>The JDK now encodes ML-KEM and ML-DSA private keys in PKCS #8 format using the DER-encoded ASN.1 CHOICE formats defined in <a href="https://www.rfc-editor.org/rfc/rfc9935.html#name-private-key-format">Section 6, &quot;Private Key Format&quot;</a> of RFC 9935 and <a href="https://www.rfc-editor.org/rfc/rfc9881.html#name-private-key-format">Section 6, &quot;Private Key Format&quot;</a> of RFC 9881. Two new security properties, <code>jdk.mlkem.pkcs8.encoding</code> and <code>jdk.mldsa.pkcs8.encoding</code>, control the encoding used when generating new keys with a <code>KeyPairGenerator</code> or when translating keys with a <code>KeyFactory</code>. Valid values are <code>seed</code>, <code>expandedKey</code>, and <code>both</code> (case-insensitive). If a system property of the same name is also specified, it supersedes the security property value. All three formats are supported when decoding previously encoded private keys with a <code>KeyFactory</code>.</p>
<p>The default encoding for newly generated ML-KEM and ML-DSA private keys is <code>seed</code>. Applications that require a particular private-key encoding can configure the relevant security property or equivalent system property.</p>
</div>
</p>
<p>
<div class="release-note"><a name="JDK-8354305"></a>
<div>security-libs/java.security</div>
<b><a href="#JDK-8354305"><span class="arrow">&#x279c;</span></a>&nbsp;SHAKE128-256 and SHAKE256-512 as MessageDigest Algorithms
</b> (<a HREF="https://bugs.java.com/bugdatabase/view_bug?bug_id=JDK-8354305">JDK-8354305</a>)
<p></p>
<p>Two new <code>MessageDigest</code> algorithms, SHAKE128-256 and SHAKE256-512, have been added to the SUN provider. These are fixed-length versions of the SHAKE128 and SHAKE256 Extendable-Output Functions (XOFs) defined in NIST FIPS 202. For more information, see <a href="https://docs.oracle.com/en/java/javase/21/security/oracle-providers.html#GUID-3A80CC46-91E1-4E47-AC51-CB7B782CEA7D">The SUN Provider</a>.</p>
</div>
</p>
<p>&nbsp;</p>
<h4>Other Notes</h4>
<p>
<div class="release-note"><a name="JDK-8382178"></a>
<div>security-libs/java.security</div>
<b><a href="#JDK-8382178"><span class="arrow">&#x279c;</span></a>&nbsp;Policy for Distrusting Certain TLS Server Certificates has Changed
</b> (JDK-8382178 (not public))
<p></p>
<p>All TLS server certificates anchored by Symantec, Entrust, and Camerfirma root CAs are now distrusted, regardless of their issuing date. TLS server certificates anchored by Chunghwa root CAs will be completely distrusted as of April 19, 2027. The <code>jdk.security.caDistrustPolicies</code> security property in the <code>java.security</code> configuration file has been updated to reflect these new policies.</p>
</div>
</p>
<p>
<div class="release-note"><a name="JDK-8386525"></a>
<div>core-libs/java.net</div>
<b><a href="#JDK-8386525"><span class="arrow">&#x279c;</span></a>&nbsp;HttpServer Validates the Host Request Header
</b> (JDK-8386525 (not public))
<p></p>
<p>The <code>com.sun.net.http.HttpServer</code> has been updated to validate the <code>Host</code> request header as described in RFC 9112. HTTP/1.1 requests without a <code>Host</code> header or with multiple <code>Host</code> headers are now rejected with an HTTP <code>400 Bad Request</code> response.</p>
<p>The validation can be disabled by setting the system property <code>sun.net.httpserver.disableHostValidation</code> to <code>true</code>.</p>
</div>
</p>
<p>
<div class="release-note"><a name="JDK-8383301"></a>
<div>core-libs/java.sql</div>
<b><a href="#JDK-8383301"><span class="arrow">&#x279c;</span></a>&nbsp;Clarification of WebRowSet.readXml Exception Behavior
</b> (JDK-8383301 (not public))
<p></p>
<p>The implementation of the <a href="https://docs.oracle.com/en/java/javase/26/docs/api/java.sql.rowset/javax/sql/rowset/WebRowSet.html#readXml(java.io.Reader)">WebRowSet.readXml</a> methods has been updated to consistently report XML parsing and validation failures as SQLException.</p>
<p><code>WebRowSet.readXml</code> validates XML input against the standard WebRowSet XML schema. Applications should expect malformed XML, schema validation failures, unsupported external entities, and other XML processing errors to be reported as <code>SQLException</code>. Validation can be disabled by setting the system property <code>jdk.sql.rowset.webrowsetValidation</code> to <code>false</code>.</p>
<p>The existing method signatures remain unchanged. No specification changes are included in this update.</p>
</div>
</p>
<p>
<div class="release-note"><a name="JDK-8382407"></a>
<div>core-libs/javax.naming</div>
<b><a href="#JDK-8382407"><span class="arrow">&#x279c;</span></a>&nbsp;Extend the Scope of com.sun.jndi.ldap.object.trustSerialData System Property to cover RMI URL References Obtained From an LDAP Context
</b> (JDK-8382407 (not public))
<p></p>
<p>The scope of the <code>com.sun.jndi.ldap.object.trustSerialData</code> system property is extended to cover transparent processing of URL RMI References obtained from an LDAP context.</p>
<p>A URL context factory is a special type of <code>ObjectFactory</code> that will be used to look up an object referred to from a JNDI <code>javax.naming.Reference</code> that does not specify any factory name, but contains a simple reference address in the form of a URL string. When deserialization of Java objects from LDAP is disabled, the JDK built-in implementation of the JNDI/LDAP provider will no longer transparently use any URL context factory when processing <code>Reference</code> objects containing a URL reference whose scheme is <code>rmi</code>.</p>
<p>To make it possible to have a finer-grain control over which URL schemes should be disabled when processing URL string reference addresses from the built-in JNDI/LDAP provider, a new system property, <code>jdk.jndi.ldap.disabledURLSchemes</code>, is introduced. The value of this property is a comma-separated list of URL schemes that are disabled. The JDK built-in implementation of the JNDI/LDAP provider will no longer transparently use any URL context factory when processing <code>Reference</code> objects containing a URL reference whose scheme corresponds (case insensitively) to one of the schemes in this list of disabled schemes. The default value for that property is &quot;rmi&quot; if <code>trustSerialData</code> is <code>false</code> (the default), and empty if <code>trustSerialData</code> is <code>true</code>. If a custom value for this new property is provided on the Java command line then only schemes listed in that property value are disabled, regardless of the value of <code>trustSerialData</code>.</p>
<p>If <code>rmi</code> is included in this list (the default when no custom values have been supplied for <code>com.sun.jndi.ldap.object.trustSerialData</code> or <code>jdk.jndi.ldap.disabledURLSchemes</code>), then a <code>javax.naming.Reference</code> object will be returned to the application instead of the object that would have been created by processing the RMI reference and looking up its URL from the context returned by a URL context factory.</p>
<p>An application that depends on following RMI URLs contained in a <code>Reference</code> obtained from a JNDI/LDAP context may need to process the <code>Reference</code> object explicitly, or provide a custom value for the <code>jdk.jndi.ldap.disabledURLSchemes</code> system property that does not include the <code>rmi</code> scheme.</p>
<p>An application that wants to prevent transparent processing of other kinds of URL schemes can now do so by supplying a custom value for the <code>jdk.jndi.ldap.disabledURLSchemes</code> system property that also includes them.</p>
</div>
</p>
<p>
<div class="release-note"><a name="JDK-8325496"></a>
<div>hotspot/runtime</div>
<b><a href="#JDK-8325496"><span class="arrow">&#x279c;</span></a>&nbsp;Make <code>TrimNativeHeapInterval</code> a Product Switch
</b> (<a HREF="https://bugs.java.com/bugdatabase/view_bug?bug_id=JDK-8325496">JDK-8325496</a>)
<p></p>
<p>(Only available on Linux with glibc.) <code>TrimNativeHeapInterval</code> has been made an official product switch. It allows the JVM to trim the native heap at periodic intervals.</p>
</div>
</p>
<p>
<div class="release-note"><a name="JDK-8333867"></a>
<div>security-libs/java.security</div>
<b><a href="#JDK-8333867"><span class="arrow">&#x279c;</span></a>&nbsp;SHA3 Performance Improved
</b> (<a HREF="https://bugs.java.com/bugdatabase/view_bug?bug_id=JDK-8333867">JDK-8333867</a>)
<p></p>
<p>The performance of the <code>MessageDigest</code> implementations that belong to the SHA3 family (SHA3-224, SHA3-256, SHA3-384, and SHA3-512) has been improved by 6-27%, depending on digested message length and on the platform used. An additional 30-40% can be experienced on AVX-512 capable platforms due to new intrinsic implementations on that platform.</p>
</div>
</p>
<p>
<div class="release-note"><a name="JDK-8387123"></a>
<div>security-libs/java.security</div>
<b><a href="#JDK-8387123"><span class="arrow">&#x279c;</span></a>&nbsp;LuxTrust Global Root CA Removed
</b> (<a HREF="https://bugs.java.com/bugdatabase/view_bug?bug_id=JDK-8387123">JDK-8387123</a>)
<p></p>

</code></pre></div>
</p>
<p>
<div class="release-note"><a name="JDK-8384736"></a>
<div>tools/jshell</div>
<b><a href="#JDK-8384736"><span class="arrow">&#x279c;</span></a>&nbsp;New JShell Remote Agent Launch Protocol
</b> (JDK-8384736 (not public))
<p></p>
<p>The way JShell's remote agents are invoked has changed. Existing agents will need to be updated to use the new protocol. See the <a href="https://docs.oracle.com/en/java/javase/21/docs/api/jdk.jshell/jdk/jshell/execution/RemoteExecutionControl.html"><code>jdk.jshell.execution.RemoteExecutionControl</code></a> JavaDoc API documentation for the new protocol.</p>
</div>
</p>
<p>
<div class="release-note"><a name="JDK-8384654"></a>
<div>xml/jaxp</div>
<b><a href="#JDK-8384654"><span class="arrow">&#x279c;</span></a>&nbsp;JAXP Templates Class Deserialization Is Disabled
</b> (JDK-8384654 (not public))
<p></p>
<p>Deserialization of the <code>com.sun.org.apache.xalan.internal.xsltc.trax.TemplatesImpl</code> class is now disabled by default. (This is an internal class that implements the <code>javax.xml.transform.Templates</code> interface.) An application attempting to deserialize an instance of this class will receive <code>UnsupportedOperationException</code>. To re-enable deserialization of this class, set the system property <code>jdk.xml.enableTemplatesImplDeserialization</code> to <code>true</code>. To take effect, this property must be set on the command line, in the <code>jaxp.properties</code> file, or in a user-defined JAXP configuration file. Prior to this change, deserialization was enabled by default, unless the Security Manager was enabled. The state of the Security Manager is no longer considered in determining whether deserialization is enabled.</p>
</div>
